## 结论与采集优先级

如果借鉴论文方法、训练末端wrench感知的PI0.5，现有29D原始状态已经有可用的六维力/力矩。
如果要对齐论文的关节力矩输入，最重要的新增数据是 **Franka七个关节的实测力矩`tau_J`**。
它与现有`O_F_ext_hat_K`、夹爪力设定值、控制器目标力矩均不同，不能相互冒充。

建议保持原29D记录不变，新增独立字段；训练时选择字段，不在采集时删掉原始通道。
本次只下载代码并整理要求，没有修改任何采集器、数据集或Python/Conda环境。

| 级别 | 建议字段/来源 | 维度与单位 | 用途 |
|---|---|---|---|
| 论文关节力矩路线必需新增 | `observation.joint_torque_raw` ← `robot_state.tau_J` | 7，N·m | 保存实测关节力矩；训练适配器将它映射成官方的`observation.effort` |
| 强烈建议同时新增，非论文强制项 | `observation.external_joint_torque` ← `robot_state.tau_ext_hat_filtered` | 7，N·m | 保存去除模型预期动力学后的低通外部力矩估计；用于接触分析和与原始力矩的消融，不能与`tau_J`混成同一通道 |
| 各方案必需；在现有时间字段上完善 | 机器人时间、主机单调时钟、两路图像时间、实际命令时间、序号/有效标志 | 各自时间基准必须注明 | 同步动作、力和图像，构造因果历史与未来标签；不同设备时间不能直接相减 |
| 各方案必需完善 | 真实任务指令、目标物体/颜色、episode成功/失败、人工接管区间 | 文本和标签 | 替换新100条示范中的`111`；不能只凭目录名猜测每条轨迹标签 |

| 推荐每次采集会话记录 | `F_T_EE`、`EE_T_K`、负载/末端质量与质心、控制模式、控制增益、滤波设置、夹爪单位及传感器版本 | 元数据，不必每帧重复 | 确认力的坐标系和参考点、标定、负载变化及不同数据批次的一致性 |

| 可选诊断 | `tau_J_d`、关节/笛卡尔接触与碰撞标志、错误状态、力矩限幅 | 各自声明单位/含义 | 排查异常、饱和与控制行为；不是论文训练的必需输入 |

Franka内部已有关节力矩传感器；不必为了获取`tau_J`另外安装六维传感器或采集电机电流。
论文的ALOHA平台用电流估算力矩，本地Franka可记录其已有实测力矩，但仍属于跨机器人适配。
本地Franky 1.1.4接口声明已经包含`tau_J`、`tau_ext_hat_filtered`、`dq`、`time`；这里只核对了声明，未连接机器人验证采样。

语义依据：`third_party/franka_reference/robot_state_0.15.3.h:211`与`:293`。
`tau_J_d`的官方说明是“不含重力的目标力矩”，不能替代实测`tau_J`。
`O_F_ext_hat_K`是作用于刚度坐标系K、用基坐标表达的估计wrench；不应直接称为TCP坐标系下的力矩。
该估计在奇异位形附近可能返回全零，因此零值也需要结合状态和有效性解释。

## 现有29维：哪些必要，哪些可以不送入模型

以下索引均从0开始，半开区间与NumPy一致。“可不输入”不等于应删除原始记录。

| 原始索引 | 数据 | 现有TCP动作＋wrench路线 | 对齐论文的关节状态＋关节力矩路线 |
|---|---|---|---|
| `[0:3]` | TCP位置3D | 保留，属于当前10D本体状态 | 非基础输入必需；保留作轨迹分析/坐标转换 |
| `[3:9]` | TCP rot6d姿态6D | 保留，与现有模型和动作表示一致 | 非基础输入必需；保留作分析/坐标转换 |
| `[9:10]` | 实测夹爪开口1D | 必需 | 必需；不要与夹爪命令单位混淆 |
| `[10:13]` | 末端外力3D | 六维wrench输入的必要部分 | 不是论文的逐关节力矩；可不作为主输入，保留作对照 |
| `[13:16]` | 末端外力矩3D | 六维wrench输入的必要部分 | 同上，不能代替七个关节的力矩 |
| `[16:19]` | TCP线速度3D | 可先不输入基础模型 | 论文主要配置未把它作为必需输入 |
| `[19:22]` | TCP角速度3D | 可先不输入基础模型 | 论文主要配置未把它作为必需输入 |
| `[22:29]` | 七关节位置7D | 纯wrench最小基线可不输入；建议保留做构型分析 | 必需，力矩含义与关节构型及重力/运动状态相关 |

因此，**最明确可从基础模型输入中暂时省略的是6D TCP速度，而不是从采集文件里删掉它们。**
若继续现有TCP策略，最小字段可为“10D位姿/夹爪＋独立6D wrench历史”；
若按Franka关节空间适配论文，则可为“7D关节位置＋1D夹爪状态＋独立7D力矩历史”。
原始数据存29D，新输入不必仍是一个29D向量；力历史应作为独立连续模态送给解码器。

官方转换器的14D是双臂布局，每侧六个转动关节加夹爪。Franka单臂有七个转动关节，不能机械截取官方前7维。
没有夹爪实测力矩时，不要补零后把它当作真实力矩监督。建议明确设定`effort_dim=7`并编写单臂映射。

现有wrench和关节位置不能准确还原实测`tau_J`。
`J(q)^T W`在参考点一致、单末端接触等假设下仅描述外部载荷的关节投影，不包含完整实测力矩中的动力学和其他接触信息。
旧数据可以继续用于wrench-aware实验，不能离线伪造“已采集的七维关节力矩”。

## 连续轨迹应如何记录

1. 在同一次机器人状态读取中保存`q`、`tau_J`、`tau_ext_hat_filtered`、`O_F_ext_hat_K`与机器人时间，并记录主机接收时间。
2. 连续记录真实动作命令和图像时间；保留接触前、接触中、调整/重试、退出的过程，不仅截取成功终点。
3. 不需要额外采集一个“未来力传感器”：未来力矩标签来自同一条记录的后续帧。
4. 现有30Hz可作为初始训练时间网格。若控制器允许，建议另存100Hz以上的力/机器人状态原始流，再按图像时间对齐或重采样；这是工程建议，不是论文明确规定的最低采样率。
5. 保留原始未归一化量、单位、关节顺序和滤波信息。标注接触/峰值力可用于评估，但论文方法不要求逐帧人工力标签。
6. 每个任务尽量覆盖不同初始位姿、接触方向、负载和重试；论文每任务400条示范是实验规模，不是训练可行性的硬门槛。

### 论文描述和开源示例的三个差异

- 论文附录A.4：过去2秒含当前帧，共10帧。示例`config.py:858`使用`[-36,-32,...,0]`，在30Hz下只有1.2秒，在示例转换器50Hz下只有0.72秒。
  本地30Hz下近似2秒的10帧偏移可取`[-60,-53,-47,-40,-33,-27,-20,-13,-7,0]`；存在时钟抖动时应按实际时间选帧。
- 论文§5符号写作从当前时刻开始的力矩chunk，但发布代码取未来`t+1..t+50`。复现发布实现应明确这个一帧偏移。
  原有`src/lab.py`小型MLP测试使用`t..t+49`，只是连通性测试，不能当作已对齐官方的VLA数据管线；本次没有改动该测试工具。
- 论文给`+obj`与`+obs+obj`使用不同β；发布代码`pi0.py:366`对未来力矩模式统一写死0.1。
  完整消融需要将β显式参数化并按对应实验设置核对，不能默认所有示例都复现了论文超参数。

## 模型框架与监督目标

官方代码基于openpi的**JAX/Flax π0**，不是本地LeRobot的PyTorch π0.5。
建议首先阅读`src/openpi/shared/effort_type.py`和`src/openpi/models/pi0.py`：

```text
RGB + 文本 → PaliGemma条件编码
关节状态 → state token
过去2秒力矩10帧 → 展平 → MLP(输入→2×1024→1024) → 单个解码器token
噪声动作序列 + 噪声未来力矩序列 → 共享action expert → 两部分flow-matching损失
```

论文推荐组合对应`EffortType.EXPERT_HIS_C_FUT`。
官方双臂力历史为10×14=140维；Franka七关节方案为10×7=70维；已有wrench方案为10×6=60维。
模型在计算损失前会将未来力矩从观测中取出，只将历史保留为条件，避免未来信息泄漏。
损失是动作与力矩对应的flow向量场MSE，而不是仅用一个独立回归头的普通动作监督。
权重加载器保留原动作投影权重，并小尺度初始化新增力矩维度；见`src/openpi/training/weight_loaders.py:96`。
推理最终返回动作部分，不把预测力矩当作机器人命令。

## 环境与权重的复现边界

官方依赖为Python≥3.11、JAX CUDA12 0.5.0、Flax 0.10.2、Transformers 4.48.1及其固定LeRobot提交。
该LeRobot源码声明数据格式v2.0；本地是LeRobot 0.5.1/v3.0，Transformers为5.3.0，不能只把仓库加入PYTHONPATH就认为兼容。
本次不安装或降级任何依赖，也不修改原Evo-RLT或当前force-VLA的环境。

两条可选路线：

- 复现官方π0：之后单独创建新的JAX环境，使用匹配的π0/openpi权重，适配Franka字段、相机和数据格式。
- 沿用本地π0.5：把官方力历史编码、解码器注入和联合flow损失移植到新代码中，继续使用已复制的PyTorch checkpoint；这属于π0.5适配，不是直接运行官方π0 checkpoint。

当前的`models/pi05_sft`不能未经权重转换和架构核对直接交给官方Orbax/JAX权重加载器。
本次完成的是源码下载、完整性/语法核对与采集设计说明，不代表完成端到端官方训练复现。
